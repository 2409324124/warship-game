## 一、约定

### 坐标系（最容易搞错，先读）

游戏世界是 three.js 右手系：**+Y 向上，+Z 船首（北），+X 西**。

> 为什么 +X 是西而不是东：右手系里 `(+x) × (+z) = −y`，而"上"是 +y，所以 `(+x, +z, +y)` 不构成
> `(东, 北, 上)` 的右手系。只有 `(+z) × (+x) = +y`… 换言之 **−x 才是东**。舵向、航向读数、海图
> 都已经按这个对齐过，不要在 Blender 里"纠正"它。

Blender 也是右手系，但 **Z 向上**。官方 glTF 导出器做 Z-up → Y-up：

```
(x, y, z)_blender  →  (x, z, −y)_gltf
```

| Blender 里 | 导出后 / 游戏里 | 含义 |
| --- | --- | --- |
| +X | +X | 西（左舷） |
| **−Y** | **+Z** | **船首方向** |
| +Z | +Y | 上 |

**在 Blender 里把模型朝 −Y 建模**（默认"前视图"正对你的方向），导出后就是船首朝 +Z，
与程序化船体完全一致。

### 单位与原点

- **1 Blender 单位 = 1 米**，`scene.unit_settings.scale_length = 1`
- **原点**：船用件放在**水线面、船体中心**——与程序化船体一致（`y = 0` 是水线，船体沿 ±Z 前后展开）
- 岛屿地标原点放在**底面**（`y = 0` 贴地）

### 命名与落点

| 类型 | 目录 | 命名 |
| --- | --- | --- |
| 挂船小件 | `public/models/props/` | `<舰key>_<部件>.glb`，如 `us_bb_floatplane.glb` |
| 岛屿地标 | `public/models/landmarks/` | `<类型>.glb`，如 `lighthouse.glb` |

工作文件 `.blend` 放 `art/blender/`，**不入库**（已在 `.gitignore` 排除，二进制只留导出结果）。

### 导出设置

- 格式 **glTF Binary (.glb)**
- 勾 **+Y up**（导出器默认）
- 导出前 **Apply Transform**
- 朝向在 Blender 里一次性摆好（机头 −Y），导出后不要再补旋转
- 材质用 **Principled BSDF**（游戏侧是 `MeshStandardMaterial`，PBR 直接对应）
- 贴图尽量嵌进 .glb，避免多文件

## 二、游戏当前上下文

### 这是什么

浏览器里的二战舰炮对战游戏（Vite + TypeScript + three.js r180）。
第一关：**一艘美军战列舰 vs 三艘日本驱逐舰**，铁底湾夜战。

### 模型现在是怎么来的（关键）

**全部是代码程序化生成的，没有任何外部资源。** 两套数据驱动：

| 数据 | 位置 | 作用 |
| --- | --- | --- |
| 船体线型 | `src/sim/hull.ts` | 站位放样：舯部 U 形（`p=3.4`）、艏部 V 形（`p=1.15`），生成蒙皮 + 甲板 |
| 舰船部件表 | `src/sim/ships.ts` | 声明式清单，建模和**命中盒共用同一份数据** |
| 炮塔/炮管规格 | `src/sim/guns.ts` 的 `TS` 表 | `len/h/w/bl/br/n/cf/fs/ss/rs/ears/hood` |
| 武器参数 | `src/sim/guns.ts` 的 `GUNS` 表 | 射程、初速、散布、装填 |

部件表里的构件类型（改舰船外观就改这些）：

```
Bx 方块（上层建筑主体，支持 rf/rr 艏艉圆角、fs 前倾、ta 顶部收分、win 舷窗带）
Cy 烟囱（rake 后倾、ov 椭圆化、pipe 烟管、cap 烟囱帽）
Ms 桅杆（tri 三脚桅、yards 横桁、top 桅顶、radar）
Pl 平台    Tt 鱼雷发射管    Aa 高炮（o/b2/b4/j2/j3/ha/ha2）
Sl 探照灯  Rf 测距仪        Dr 指挥仪   Bt 吊艇/小艇
Cp 弹射器  Cr 起重机        Gm 固定炮座  Dc 深弹架   Tu 炮塔（挂在 tur 数组里）
```

渲染侧：`src/render/shipModel.ts` 把上面这些翻译成几何体，`src/render/shipView.ts` 每帧同步
位置/摇摆/炮塔转动/沉没。**船体、上层建筑、舰炮都是箱体与回转体的堆叠**——这正是程序化擅长的，
也是"哪些该在 Blender 里做"的判断依据。

| `jp_bb` | 金刚级 | 4×II 14"（艏2艉2） | 12×I 6" 舷侧炮廓 | 宝塔桅层级偏少 |
| `us_ca` | 新奥尔良级 | 3×III 8"/55（艏2艉1） | 4×II 5" | 副炮应为 8 门单装 |

| `jp_dd` | 吹雪级 | 3×II 127mm | — | 第一关敌舰，3 艘同屏 |

改配置会红——**这是故意的**，改之前先确认资料。

### 接口（当前只支持 props / landmarks，舰岛与炮塔的覆盖尚未接线）

`src/render/assets.ts`：

```ts
loadModel(name)                       // 加载 /models/<name>.glb，缺失时返回 null 不报错
mountProps(parent, props, deckAt)     // 按 { model, z, y?, x?, ry?, scale? } 挂到父节点
```

- **现在没有任何地方 import 它**，所以不进包、不生效（构建产物 591 kB，与加它之前完全一致）
- GLTFLoader 是懒加载的，只在第一次真正加载时才拉进来
- 文件缺失 → 静默跳过，游戏照常跑

已经就位的：`loadModel()` / `mountProps()` 能加载任意 .glb 并按船体局部坐标挂载，
文件缺失时静默跳过。**舰岛与炮塔的"覆盖"逻辑还没接**——需要：

1. `render/shipView.ts`：
   - 舰岛：若 `ships/<key>_super.glb` 存在，加载后加入 `group`，并**隐藏**程序化的
     `struct` / `dark` 两个 mesh（保留 hull / deck / foam）
   - 炮塔：若 `guns/<kind>.glb` 存在，用它的 `base` / `barrel` 替换程序化炮塔几何，
     挂到现有 pivot 上（`barrel` 节点继续吃 `elev`）
2. 缺失时什么都不做，程序化几何照常显示（回退）
3. 舰船数据不需要改——按 key 和 turret kind 自动匹配文件名

这一步属于**接口实现**，不是建模；要不要现在做取决于你想先定文档还是先通管线。

### 命中盒

命中判定用的是 `spec.L / B / F / top` + `segHitShip()` 的盒体测试，**与渲染几何无关**。
所以装饰件做得再精细也不会影响命中——这也是"Blender 件只管好看"的底气。

## 三、要做什么

### 分工原则

**Blender 负责所有舰岛与所有舰炮。** 程序化只保留船体、甲板、水线与命中盒。

Blender 做：

- **舰岛（上层建筑）全套**：塔式/宝塔式舰桥、舰桥围壁与舷窗带、烟囱与烟囱帽、
  桅杆与桁架（含格子桅、金刚的宝塔桁架）、探照灯平台、指挥仪、雷达、测距仪、
  吊艇架与救生艇、弹射器、起重机、机炮座、舷侧走道与栏杆
- **舰炮全套**：主炮塔（塔体、炮盾、炮管、炮口、测距仪耳）、副炮塔/炮廓炮、鱼雷发射管
- **有机/异形件**：水上侦察机 + 浮筒、螺旋桨、锚、系缆桩
- **岛屿地标**：灯塔、椰树、栈桥、沉船

程序化保留：

- 船体蒙皮与甲板（`src/sim/hull.ts` 站位放样）
- 水线泡沫、尾流等特效
- **命中盒**（见下）

### 关键后果：视觉与命中盒必须分离

现在 `sim/ships.ts` 的 `parts` 一份数据同时喂**渲染**和**命中盒**（`segHitShip` 用的是
`spec.L / B / F / top` 的大盒体，其实不依赖 `parts`，但视觉上它们是一体的）。
舰岛和舰炮交给 Blender 之后，这条链要断开：

- **外观**：来自 `public/models/` 下的 .glb
- **命中**：仍由 `sim/ships.ts` 的数据决定（盒体 + `parts` 作为可选的细化体积）
- `parts` 里的方块**不再需要长得好看了**——它们退化为"碰撞体积"描述，
  可以保留、简化，甚至在接口就绪后删除；改它们不会改变玩家看到的东西
- 炮塔的**方位转动与俯仰仍由 `updateTurrets()` 驱动**，Blender 的炮塔模型挂到同一个
  pivot 上即可，不需要在 Blender 里做动画

**回退规则（重要）**：任何 .glb 缺失时，游戏必须仍然用程序化几何正常运行。
Blender 是"覆盖"而不是"替换"——`没有文件 → 用代码生成的`，这样才能边建模边跑。

### 炮塔模型的节点约定

炮塔 .glb 里放两个**同级**节点，靠名字识别：

| 节点名 | 内容 | 运动 |
| --- | --- | --- |
| `base` | 炮塔座圈与塔体（不含炮管） | 随 `pivot.rotation.y` 做方位转动 |
| `barrel` | 炮管 + 炮盾 + 炮尾 | 绕自身 X 轴俯仰（`barrel.rotation.x = -elev`） |

- 原点：`base` 的原点 = **炮塔座圈中心（甲板面高度）**
- 朝向：炮管朝 **−Y**（导出后即世界 +Z 船首）
- 枢轴：`barrel` 的原点放在**耳轴**位置（大约在塔体中部、炮管根处）
- 单位米，1:1

### 文件清单与命名

| 类型 | 路径 | 说明 |
| --- | --- | --- |
| 舰岛 | `public/models/ships/<舰key>_super.glb` | 整舰上层建筑，原点船体中心水线，朝 −Y |
| 炮塔 | `public/models/guns/<TS 里的 kind>.glb` | 如 `us16t.glb`、`us5d.glb`、`jp14d.glb` |
| 挂船小件 | `public/models/props/<舰key>_<部件>.glb` | 可选，舰岛已包含的不用单独做 |
| 岛屿地标 | `public/models/landmarks/<类型>.glb` | |

`TS` 里现有的 kind：`us5s us5d us6t us8t us16t jp5d jp5s jp55 jp8d jp14d jp6c`

### 已知限制（影响"怎么判断做得对不对"）

目前**没有**几何互穿检测、没有粒子与舰体的碰撞、没有正交/线框检视模式。
所以判断一个部件做得对不对，现阶段只能在 Blender 里直接看，或者导出后靠游戏里的透视截图——
都不够。补上这几项（模型体检工具、检视模式、特效碰撞）是另一件事，不在这个工作区的范围里。

## 四、快速上手

```bash
# 1. 在 Blender 里建模，工作文件存
#    art/blender/<名字>.blend
# 2. 朝 −Y 建模，1 单位 = 1 米
#    舰岛原点 = 船体中心水线；炮塔原点 = 座圈中心（甲板面）
# 3. 导出 glTF Binary (.glb)，+Y up，Apply Transform
#    → public/models/ships/<舰key>_super.glb      舰岛
#    → public/models/guns/<turret kind>.glb       炮塔（内含 base / barrel 两个节点）
#    → public/models/props/<舰key>_<部件>.glb     可选小件
#    → public/models/landmarks/<类型>.glb         地标
# 4. 文件一落地，游戏下次刷新就会用它（覆盖逻辑接好之后）
```

游戏跑起来：`npm run dev` → http://127.0.0.1:5173
验证：`npm test`（37 项）、`npm run typecheck`、`npm run build`、`npm run smoke`（无头截图 + 探针）
